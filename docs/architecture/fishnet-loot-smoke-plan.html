서버가 확정하는 Loot 흐름 한 장 정리

이 문서는 현재 스테이지에 올라간 FishNet 서버 권한 Loot 스모크 작업물을 설명회/리뷰용으로 정리한 HTML 문서입니다. 핵심은 클라이언트가 “먹었다”를 확정하지 않고, 서버가 requestId, 거리, 아이템 상태를 검증한 뒤 owner와 상태를 확정한다는 점입니다.

1. ADR 요약

제목

FishNet 서버 권한 Loot 스모크 1차 구현 플랜

상태

제안/검증 중 코드와 프리팹 wiring은 1차 구현 범위에 들어왔고, Unity Editor import 및 MPPM Host/Client 런타임 로그 확인은 후속 검증으로 남습니다.

배경

ProjectRaidAuthority의 MVP 핵심 검증 순서는 서버 권위 코어 → 전투 판정 → 인벤토리 무결성입니다. Loot는 인벤토리 무결성의 첫 관문이므로, 클라이언트 확정이 아닌 서버 확정 흐름을 먼저 스모크로 증명합니다.

결정

  • 클라이언트는 가까운 LootItem 후보를 찾고 E 입력을 ServerRpc로 보냅니다.
  • 서버는 requestId 중복, itemId 유효성, 거리, 이미 획득 여부를 순서대로 검증합니다.
  • 성공 시 서버만 LootItem.State와 LootOwnerId를 변경합니다.
  • 성공/실패/중복은 로그 문자열로 확인 가능하게 남깁니다.

결과와 영향

현재 단계에서는 UI/인벤토리 저장소까지 확장하지 않고, “서버가 Loot 결과를 확정한다”는 최소 증거를 만들었습니다. 이후 전투 보상, 아이템 persistence, extraction 결과 저장으로 확장할 수 있습니다.

ADR 의존성

  • FishNet NetworkObject, NetworkBehaviour, ServerRpc
  • Unity Input System Keyboard.current.eKey
  • 현재 00_FishNetNetworkFlow 씬 전환/스폰 구조

엔진 호환성

Unity/FishNet 단일 프로젝트 안에서 Client/Server/Shared 폴더를 나누는 책임 분리 방식입니다. 빌드 분리는 아직 목표가 아닙니다.

연결된 GDD 요구사항

서버 권위, 전리품 무결성, 레이드 보상 확정 요구사항과 연결됩니다. 안정 ID 연결은 추후 tr-registry.yaml 반영 대상입니다.

2. 한 줄 결론

클라이언트는 Loot를 “요청”만 하고, 서버가 모든 검증을 통과한 경우에만 Loot를 “확정”합니다.

입력

E 키를 누르면 owner 클라이언트가 가까운 LootItem 후보를 찾습니다.

요청

requestId와 itemId를 ServerRequestLoot로 전송합니다.

검증

서버가 중복, 유효성, 거리, 아이템 상태를 순서대로 확인합니다.

확정

서버가 ServerMarkLooted(OwnerId)로 소유자를 기록합니다.

3. 책임 분리

영역현재 책임절대 하지 않는 일
Client Owner 입력 감지, 주변 LootItem 후보 검색, 요청 ID 생성, ServerRpc 호출 아이템 owner 확정, 상태 변경, 이미 획득 여부 최종 판정
Server 요청 중복 처리, itemId/거리/상태 검증, Loot owner 확정, 성공/실패 로그 출력 클라이언트 UI 표현, 입력 수집
Shared LootRequest, LootResult, LootItemIdentity, LootRequestId, LootItemState 같은 값 계약 제공 서버 판정 로직, 클라이언트 표현 로직
반지름이 둘로 나뉜 이유: 클라이언트 후보 검색 반경은 2.25m, 서버 수락 반경은 2.5m입니다. 클라이언트는 편의상 후보를 찾을 뿐이고, 서버가 약간의 허용치를 둔 최종 판정을 내립니다.

4. 공유 계약 타입

LootItemIdentity

전리품 prefab 인스턴스를 구분하는 문자열 값입니다. 비어 있으면 유효하지 않은 요청입니다.

LootRequestId

같은 요청을 두 번 처리하지 않기 위한 요청 식별자입니다. 현재는 owner id, 증가 시퀀스, GUID를 조합합니다.

LootRequest

클라이언트가 서버에 보내는 최소 요청 값입니다. requestId와 itemId가 모두 있어야 유효합니다.

LootItemState

Available 또는 Looted만 가진 최소 상태 enum입니다.

LootResult

서버 판정 결과를 로그/검증에 일관되게 쓰기 위한 값입니다. 성공 여부, owner, 상태, 사유를 담습니다.

LootItem

테스트용 NetworkBehaviour입니다. 서버 확정 상태인 state와 ownerId를 보관합니다.

5. Loot 요청 시퀀스

  1. Gameplay 진입 후 서버가 LootItem을 스폰합니다. SpawnSmokeLootItem이 lootItemPrefab을 (0, 0.5, 3) 위치에 스폰합니다.
  2. Owner 클라이언트가 E 키를 누릅니다. SendOwnedLootInput은 owner의 로컬 입력에서만 실행됩니다.
  3. 클라이언트가 가장 가까운 사용 가능 아이템 후보를 찾습니다. 이 후보 선택은 편의 기능일 뿐 최종 판정이 아닙니다.
  4. 서버가 ServerRpc를 받습니다. 문자열로 온 값을 LootRequest 계약으로 감싸고 검증을 시작합니다.
  5. 서버가 통과/거절/중복을 결정합니다. 성공만 ServerMarkLooted로 상태를 바꿉니다.

6. 서버 판정 다이어그램

중복 요청은 실패가 아니라 무시입니다. 같은 requestId가 다시 들어오면 서버는 상태를 바꾸지 않고 Duplicate LootRequest ignored 로그만 남깁니다. 이미 다른 요청으로 획득된 아이템을 다시 먹으려는 경우는 LootRejected입니다.

8. 검증 로그와 체크 방법

성공 로그

[FishNet Authority Smoke] LootCommitted

owner, requestId, itemId, state가 함께 출력되면 서버 확정 경로를 탄 것입니다.

실패 로그

[FishNet Authority Smoke] LootRejected

Invalid, not found, out of range, already looted 사유를 확인합니다.

중복 로그

[FishNet Authority Smoke] Duplicate LootRequest ignored

같은 requestId가 재전송되어도 상태가 다시 바뀌지 않아야 합니다.

확인 단계기대 결과이유
Host/Server 시작 후 Gameplay 진입 LootItem 스폰 로그와 아이템 NetworkObject 존재 서버가 테스트용 아이템을 소유한 상태로 시작해야 함
LootItem 근처에서 owner 클라이언트가 E 입력 LootCommitted 로그 클라이언트 요청 → 서버 검증 → 서버 확정 경로 확인
멀리 떨어져 E 입력 또는 잘못된 itemId 요청 LootRejected 로그 서버가 클라이언트 요청을 무조건 믿지 않는지 확인
이미 Looted 상태인 아이템 재요청 LootRejected with already looted 한 아이템의 owner가 중복 확정되지 않아야 함

9. 남은 검증/한계

아직 후속 검증이 필요한 것

  • Unity Editor import 후 compile error가 없는지 확인
  • MPPM Host 1개 + Client 1개 이상으로 실제 Loot 성공 로그 확인
  • 중복 요청과 이미 획득된 아이템 재요청 시나리오를 런타임에서 재현
  • prefab이 FishNet spawnable/prefab 참조에 올바르게 연결되었는지 확인

의도적으로 하지 않은 것

  • 인벤토리 저장, 보상 persistence, 추출 결과 저장
  • Loot UI/피드백 완성
  • 클라이언트 prediction/reconcile
  • 복수 아이템 테이블, 드랍 확률, 보상 밸런싱
