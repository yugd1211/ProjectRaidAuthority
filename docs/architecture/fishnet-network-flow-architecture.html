1. ADR 요약

제목

FishNet 기반 Bootstrap → Match Room → Gameplay 네트워크 플로우 설계

상태

제안 설명회 및 구현 전 검토용. 아직 승인 ADR은 아닙니다.

배경

현재 Network Flow은 MPPM 자동 실행, FishNet 연결, MatchRoom 준비, Gameplay 서버 권한 이동 검증을 한 흐름에 담고 있습니다. 그러나 FishNet의 코어 개념과 프로젝트의 Lobby/Room 용어가 섞이면 설명과 확장이 어려워집니다.

결정

프로젝트 용어로 Match Room을 유지하되 FishNet 내장 개념이 아니라 프로젝트 레벨 조합 계층으로 명확히 표시합니다. RoomPlayer는 룸 단계의 플레이어별 임시 상태를 담당하고, Gameplay 영속 상태는 별도 snapshot/service로 승격합니다.

결과와 영향

  • Ready, 팀, 캐릭터 선택, 로딩 완료 같은 소유자별 룸 상태를 확장하기 쉬워집니다.
  • FishNetNetworkFlowController가 비대해지는 것을 장기적으로 막을 수 있습니다.
  • 현재 구현과 권장 진화를 분리해 설명회에서 오해를 줄입니다.
  • 로비/매치메이킹 계층은 인터페이스로 추상화하고, 현재는 단일 고정 서버를 반환하는 구현체로 둡니다.

ADR 의존성

  • FishNet NetworkManager, SceneManager, DefaultScene
  • FishNet NetworkObject, NetworkBehaviour, ServerRpc, SyncVar
  • Unity Multiplayer Play Mode 태그 기반 실행

엔진 호환성 / 연결된 GDD 요구사항

Unity 6 계열 프로젝트와 현재 FishNet 패키지 기준입니다. GDD 요구사항은 아직 별도 ID로 연결되지 않았으므로 구현 전 tr-registry.yaml 반영이 필요합니다.

2. RALPLAN-DR 결정 요약

Principles

  1. FishNet 코어와 프로젝트 도메인 용어를 섞지 않는다.
  2. 서버 권한과 플레이어별 상태를 명확히 분리한다.
  3. Room 단계 상태는 임시, Gameplay 상태는 명시적으로 승격한다.
  4. 현재 구현과 권장 진화를 문서에서 항상 라벨링한다.
  5. 외부 로비/매치메이킹 서비스 선택은 FishNet 내부 룸/게임플레이 구조에 새지 않게 한다.

Decision Drivers

  1. 설명회에서 이해 가능한 단순성
  2. 팀/캐릭터 선택/Ready/로딩 완료로 확장 가능한 구조
  3. FishNet의 NetworkObject/SceneManager 사용 흐름과 충돌하지 않는 책임 분리

결론

RoomPlayer 유지

단기 Network Flow에서는 과해 보일 수 있지만, 장기적으로 룸 단계의 플레이어별 상태를 담는 가장 자연스러운 단위입니다.

대안 비교

대안장점단점판단
A. RoomPlayer 유지 소유자별 Ready/팀/캐릭터/로드 상태를 NetworkBehaviour, SyncVar, ServerRpc로 자연스럽게 표현합니다. 작은 Network Flow에서는 객체가 많아 보입니다. 씬 전환 후 상태 승격 규칙이 필요합니다. 채택
B. NetworkFlowController Dictionary 집중 파일 수가 줄고 초기 설명이 쉽습니다. NetworkFlowController가 연결, 상태, RPC, 씬, 스폰을 모두 떠안아 장기적으로 비대해집니다. 현재 설명회 단순화에는 가능하지만 장기 구조에는 부적합
C. MatchRoom 제거 후 바로 Gameplay MPPM 스모크 테스트는 가장 빠릅니다. Lobby/Room/Ready/선택 구조를 나중에 다시 설계해야 합니다. 단기 테스트 전용 옵션

3. FishNet 용어와 프로젝트 용어 분리

중요: 현재 프로젝트의 FishNetNetworkFlowController와 MatchRoom은 FishNet이 제공하는 내장 Room/Lobby 시스템이 아닙니다. FishNet 코어는 주로 네트워크 매니저, 씬 동기화, 네트워크 오브젝트, RPC, 동기화 타입을 제공합니다.
구분의미현재 프로젝트 대응
FishNet SceneManager 서버와 클라이언트의 네트워크 씬 로드/언로드와 이벤트 콜백을 관리합니다. FishNetNetworkFlowController가 OnClientLoadedStartScenes, OnLoadEnd, LoadGlobalScenes를 사용합니다.
FishNet DefaultScene 간단한 offline/online scene 전환을 도와주는 컴포넌트입니다. OfflineBootstrap에서 접속 후 MatchRoom으로 이동하는 기본 경로를 설정합니다.
FishNet NetworkObject 서버가 spawn하고 클라이언트에 동기화하는 네트워크 GameObject 단위입니다. RoomPlayer.prefab, GamePlayer.prefab
FishNet NetworkBehaviour RPC, SyncVar, ownership, server/client 상태 접근을 사용하는 스크립트 기반입니다. RoomPlayer, GamePlayer
프로젝트 Lobby 매치 찾기, 파티, 방 목록, 초대 등 상위 UX/서비스 계층입니다. 현재 Network Flow에는 아직 없음. 장기적으로 별도 서비스/화면으로 분리 권장.
프로젝트 Match Room 특정 매치 시작 전 참여자 상태를 맞추는 대기방입니다. MatchRoom + RoomPlayer

4. 로비/매치메이킹 추상화 전략

결정: 지금은 외부 로비/매치메이킹 서비스를 붙이지 않습니다. 대신 인터페이스를 먼저 정의하고, 현재 구현체는 서버 1개를 자동 선택하는 SingleServerMatchmaker로 둡니다. 나중에 Unity Lobby/Matchmaker, Steam Lobby, PlayFab, Nakama, Custom Backend로 교체할 수 있게 합니다.

현재 구현 방향

  1. server 태그 인스턴스는 FishNet 서버를 시작합니다.
  2. player 계열 인스턴스는 Matchmaking 추상화에 매치를 요청합니다.
  3. SingleServerMatchmaker가 localhost와 개발용 room 정보를 반환합니다.
  4. Bootstrap 계층이 반환된 주소로 ClientManager.StartConnection(address)를 호출합니다.
  5. 접속 후에는 기존 FishNet Match Room / Gameplay 플로우를 탑니다.

나중에 교체 가능한 구현체

  • UnityMatchmakerService: Unity Lobby/Matchmaker/Relay 또는 Dedicated Server Hosting 연동
  • SteamLobbyMatchmaker: Steam Lobby metadata와 친구 초대 기반 방 선택
  • PlayFabMatchmaker: PlayFab Matchmaking + Multiplayer Servers 연동
  • NakamaMatchmaker: Nakama party/matchmaker/custom server 연동
  • CustomBackendMatchmaker: 자체 Lobby API / Server Allocator 연동

권장 인터페이스 형태

public interface IMatchmakingService
{
    Task<MatchAssignment> FindMatchAsync(MatchRequest request);
}

public sealed class MatchAssignment
{
    public string Address;     // FishNet 접속 주소
    public ushort Port;        // Transport 포트
    public string RoomId;      // 외부 로비/매치 식별자
    public string AuthToken;   // 서버 입장 검증 토큰, 개발 단계에서는 dev 값
}
계층알아야 하는 것알면 안 되는 것
Lobby/Matchmaking 플레이어 조건, 지역, 모드, 방 목록, 서버 주소, 입장 토큰 RoomPlayer, GamePlayer, FishNet scene 내부 구현
FishNet Bootstrap MatchAssignment의 주소/포트/토큰, server/client 실행 역할 어떤 외부 서비스가 매칭을 수행했는지의 세부 API
Match Room 이미 접속한 connection, Ready/팀/캐릭터/로드 상태 방 목록 검색, 외부 matchmaking ticket 처리
Gameplay 서버 권한 입력/전투/상호작용/결과 로비 UI, 방 검색 조건, 외부 lobby metadata

이 추상화를 두면 현재는 단일 서버 자동 선택으로 빠르게 진행하면서도, 나중에 Steam/Unity/PlayFab 등으로 바꿀 때 FishNet 내부 Room/Gameplay 구조를 크게 흔들지 않아도 됩니다.

5. 권장 전체 구조 다이어그램

현재 구현 현재는 FishNetNetworkFlowController 하나가 위 서비스 대부분을 담당합니다. 권장 진화 기능이 늘어나면 위처럼 책임 단위로 분리합니다.

6. 현재 씬 플로우와 권장 진화

현재 구현

권장 진화

  1. Bootstrap: 실행 환경과 역할만 판정합니다.
  2. Lobby: 매치 찾기, 방 목록, 파티, 초대 등 UX/서비스 계층입니다.
  3. Match Room: 특정 매치 참가자별 Ready/선택/로드 상태를 관리합니다.
  4. Gameplay: 서버 권한 이동, 전투, 상호작용, 결과 저장을 담당합니다.

장기 구조에서는 MatchRoom을 “FishNet의 Room 기능”으로 설명하지 말고, 프로젝트의 Match Room으로 설명합니다.

7. 통신 시퀀스

Room 단계 통신

  • 클라이언트 소유 RoomPlayer가 Ready/선택 입력을 받습니다.
  • 입력은 ServerRpc로 서버에 전달됩니다.
  • 서버가 SyncVar를 변경하고 클라이언트가 동기화된 상태를 봅니다.

Gameplay 단계 통신

  • 클라이언트는 이동 의도를 ServerRpc로 보냅니다.
  • 서버가 이동/회전을 적용합니다.
  • NetworkTransform이 결과를 관찰자에게 동기화해야 합니다.

8. 객체별 책임

객체현재 책임현재 한계권장 진화
FishNetMppmRoleBootstrapper MPPM 태그를 읽어 server면 서버 전용, 그 외는 localhost 클라이언트로 시작합니다. Unity Editor/MPPM 전용 성격이 강합니다. NetworkBootstrapService로 이름과 책임을 일반화합니다.
FishNetNetworkFlowController 연결 시작, FishNet SceneManager 이벤트 구독, RoomPlayer spawn, Ready 집계, Gameplay 로드, GamePlayer spawn을 담당합니다. 하나의 클래스가 너무 많은 orchestration 책임을 갖습니다. SceneFlowService, RoomSessionService, PlayerSpawnService로 분해합니다.
RoomPlayer 룸 단계의 소유자별 Ready 상태를 SyncVar로 보관하고 ServerRpc로 변경합니다. Gameplay 씬 전환 후 영속 상태 저장소로 쓰면 안 됩니다. Ready, 팀, 캐릭터 선택, 로드 완료를 담는 MatchParticipant 네트워크 표현으로 확장합니다.
GamePlayer 클라이언트 입력을 서버로 보내고 서버가 이동/회전을 적용하는 게임플레이 플레이어입니다. NetworkTransform prefab 설정이 서버 권한 의도와 일치하는지 검증이 필요합니다. GameplayAuthorityService와 연동해 이동, 전투, 상호작용 검증을 서버 중심으로 확장합니다.
NetworkFlowAudioListenerGuard MPPM/씬 전환 중 AudioListener를 하나로 유지합니다. Network Flow 보조 유틸리티입니다. 카메라/오디오 시스템이 확정되면 공통 presentation 계층으로 이동합니다.

10. RoomPlayer 유지 이유와 생명주기

왜 NetworkFlowController에 넣지 않는가?

Ready, 팀, 캐릭터 선택, 로드 완료는 플레이어별 상태입니다. 이를 모두 FishNetNetworkFlowController의 Dictionary에 넣으면 NetworkFlowController가 상태 저장소, RPC 입구, 씬 전환자, 스폰 관리자 역할을 동시에 맡게 됩니다.

반면 RoomPlayer는 FishNet ownership과 잘 맞습니다. 소유 클라이언트는 자기 RoomPlayer를 통해 요청하고, 서버가 검증 후 SyncVar를 갱신합니다.

생명주기 경계

  1. 클라이언트가 MatchRoom start scene을 로드합니다.
  2. 서버가 connection별 RoomPlayer를 spawn합니다.
  3. RoomPlayer가 Ready/선택/로드 상태를 관리합니다.
  4. Gameplay 진입 직전 필요한 값만 MatchParticipant snapshot으로 승격합니다.
  5. Gameplay 씬에서는 GamePlayer와 gameplay service가 권한을 담당합니다.

경계: RoomPlayer를 결과 저장, 전투 상태, 추출 결과, 영속 플레이어 데이터의 소유자로 확장하지 않습니다. RoomPlayer는 Match Room 단계의 임시 참여자 표현입니다.

11. 현재 한계와 구현 전 체크리스트

현재 한계: GamePlayer 코드는 서버가 이동을 적용하는 의도를 갖지만, 현재 GamePlayer.prefab의 NetworkTransform 설정은 서버 권한 의도와 일치하는지 반드시 확인해야 합니다. 이 문서는 “서버 권한 이동 검증 완료”를 주장하지 않습니다.
