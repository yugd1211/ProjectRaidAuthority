# 서버 권위 기반 탑다운 로그라이크 익스트랙션 게임 개발 계획서

- 문서 목적: PM 관점에서 기능 개발 우선순위, 개발 플로우, 기간 설정, MVP 범위, 단계별 완료 기준을 정의한다.
- 프로젝트 전제: Unity 기반, 1인 개발, 6개월 MVP, 서버 권위 데디케이트 서버 구조, 탑다운 로그라이크 익스트랙션 장르.
- 핵심 방향: 콘텐츠 양보다 서버 권위 구조, 전투 판정, 인벤토리 무결성, 레이드 완주 플로우를 먼저 검증한다.

---

## 1. 프로젝트 한 줄 정의

**탑다운 익스트랙션 레이드 구조에 로그라이크식 런 빌드 선택을 결합하고, 전투·인벤토리·탈출 결과를 서버 권위로 확정하는 4~8인 PvE 중심 멀티플레이 MVP.**

---

## 2. PM 기준 개발 우선순위 원칙

개발 우선순위는 아래 4개 기준으로 판단한다.

| 기준 | 설명 | 적용 예시 |
|---|---|---|
| 의존성 | 뒤 기능이 앞 기능에 기대는가 | 특성 시스템은 전투/상태이상/저장 구조 이후 개발 |
| 리스크 제거 | 실패 시 전체 일정이 무너지는가 | 서버 판정, 인벤토리 중복, 레이드 결과 저장 |
| 포트폴리오 가치 | 프로젝트 차별점을 증명하는가 | 서버 권위, 치트 대응, Docker 운영 |
| 콘텐츠 증폭력 | 적은 구현으로 플레이 변주를 만드는가 | 특성/시너지/저주 |

### 결론

**콘텐츠보다 서버 코어를 먼저 개발한다.**

잘못된 순서:

```text
UI → 특성 → 아이템 → 전투 → 서버
```

권장 순서:

```text
서버 코어 → 전투 판정 → 인벤토리 무결성 → 레이드 플로우 → 로그라이크 레이어 → 운영/최적화
```

---

## 3. 전체 개발 순서 요약

| 순서 | 개발 항목 | 예상 기간 | 우선순위 | 완료 기준 |
|---:|---|---:|---|---|
| 1 | 서버 뼈대, Tick, Snapshot, Entity 구조 | 1~2주 | 필수 | 데디 서버 실행, 클라이언트 접속, 더미 엔티티 동기화 |
| 2 | 이동, 조준, 발사, 서버 히트 판정 | 3~4주 | 필수 | 서버 기준 위치/HP 변화 확정 |
| 3 | 기본 AI, 상태이상, 피격/사망 처리 | 1~2주 | 필수 | AI 탐지/추적/공격, 출혈 등 상태이상 처리 |
| 4 | 인벤토리, 루팅, 아이템 소유권 | 2~3주 | 필수 | 아이템 중복 없음, 루팅 요청 멱등 처리 |
| 5 | 레이드 입장/탈출/결과 저장 | 2~3주 | 필수 | 입장→교전→루팅→탈출→저장 1회 완주 |
| 6 | 특성 8개, 시너지 4개, 저주 3개 | 3~4주 | 필수 | 3지선다 선택, 태그 기반 시너지 적용 |
| 7 | 고위험 탈출, 메타 해금, 환경 이벤트 | 3~4주 | 선택/필수 혼합 | 반복 플레이 동기와 리스크 보상 구조 확인 |
| 8 | Docker, 로그, 운영, 최적화, QA | 4주 | 필수 | 멀티 인스턴스 실행, 테스트 로그 확보 |

## 4. 개발 플로우

PM 운영 방식은 **단계형 + 게이트형**으로 진행한다.  
각 단계 종료 시 다음 단계로 넘어갈 수 있는 기준을 반드시 확인한다.

```text
기획 정의
  ↓
기술 스파이크
  ↓
서버 권위 코어
  ↓
전투/AI 코어
  ↓
인벤토리/레이드 세로 슬라이스
  ↓
로그라이크 레이어
  ↓
운영/최적화/QA
  ↓
포트폴리오 빌드 패키징
```

## 5. Phase별 세부 계획

## Phase 0. 프리프로덕션 / 정의

- 기간: 1~2주
- 목표: 개발 방향, 서버 권위 범위, MVP 스코프 확정

### 주요 작업

| 작업 | 설명 | 산출물 |
|---|---|---|
| PRD 작성 | 핵심 목표, 타겟, MVP 범위 정의 | PRD 1차 문서 |
| GDD Lite 작성 | Core Loop, Meta Loop, Retention 구조 정의 | 기획 요약 문서 |
| 서버 권위 범위 정의 | 서버가 확정할 항목과 클라 표시 항목 분리 | 서버 권한 표 |
| 데이터 모델 초안 | Entity, Player, Item, Raid, Trait 구조 정의 | 데이터 스키마 초안 |
| MVP 제외 항목 정의 | PvP, 거래소, 다중 맵 등 제외 | 제외 리스트 |

### 게이트 기준

- 서버가 확정할 항목이 문서화되어 있어야 한다.
- 6개월 내 구현하지 않을 기능이 명확해야 한다.
- Core Loop가 한 문장으로 설명되어야 한다.

### Core Loop

```text
레이드 입장 → 탐색/루팅 → 교전 → 특성 선택 → 탈출 선택 → 결과 저장 → 메타 해금
```

---

## Phase 1. 서버 권위 코어 구축

- 기간: 1~4주
- 목표: 서버가 월드를 소유하고 클라이언트는 입력만 보내는 구조 구축

### 주요 기능

| 기능 | 상세 | 우선순위 |
|---|---|---|
| Dedicated Server 실행 | Unity Headless/Dedicated Server 빌드 | 필수 |
| Tick Loop | 20~30Hz 기준 서버 시뮬레이션 루프 | 필수 |
| ClientInput | 이동, 조준, 발사 입력 메시지 | 필수 |
| WorldSnapshot | 위치, 회전, HP, 상태 비트 전송 | 필수 |
| Entity Registry | 서버 내 EntityId 기반 오브젝트 관리 | 필수 |
| AOI 초안 | 플레이어 주변 엔티티만 전송 | 선택/초기 |

### 서버 입력/출력 기본 구조

```text
Client
  → ClientInput(tick, seq, moveVec, aimDir, fire, reload, interact)
Server
  → Validate Input
  → Simulate World
  → WorldSnapshot(serverTick, entities, hp, status)
Client
  → Interpolation / UI / Effect
```

### 완료 기준

- 클라이언트 1~2개가 서버에 접속 가능하다.
- 서버 기준 위치가 클라이언트에 동기화된다.
- 클라이언트가 위치를 직접 확정하지 않는다.
- 더미 엔티티가 서버 Tick에 따라 움직인다.

### 리스크

| 리스크 | 원인 | 완화책 |
|---|---|---|
| 서버/클라 책임 혼재 | 임시 구현으로 클라 계산 증가 | 모든 상태 변경 함수에 서버 전용 검증 추가 |
| Tick 불안정 | Update 기반 임시 처리 | Fixed Tick Manager 분리 |
| 스냅샷 과다 | 모든 엔티티 전체 전송 | AOI와 상태 압축을 초기부터 고려 |

## Phase 2. 전투 코어 / AI 코어

- 기간: 5~8주
- 목표: 전투가 서버 기준으로 성립하는 상태 만들기

### 주요 기능

| 기능 | 상세 | 우선순위 |
|---|---|---|
| 이동 검증 | 속도, 대시, 위치 보정 | 필수 |
| 조준/발사 | 클라 입력, 서버 판정 | 필수 |
| 히트스캔 판정 | 서버 Raycast 또는 충돌 판정 | 필수 |
| HP/피해 처리 | DamageApplied 이벤트 | 필수 |
| 상태이상 | 출혈/화상/감전 중 최소 1~2종 | 필수 |
| 기본 AI | 탐지, 추적, 공격, 사망 | 필수 |
| 피격 피드백 | 서버 확정 후 이펙트/UI 표시 | 필수 |

### 전투 처리 흐름

```text
Client Fire Input
  ↓
Server Validate Weapon State
  ↓
Server Hit Check
  ↓
Damage Calculation
  ↓
StatusEffect Apply
  ↓
Broadcast Confirmed Event
```

### 완료 기준

- 적에게 총을 쏘면 서버 기준으로 HP가 감소한다.
- 클라에서 임의로 피해량을 바꿀 수 없다.
- 상태이상 Tick 피해가 서버에서 처리된다.
- AI가 서버에서 탐지/추적/공격한다.

### 리스크

| 리스크 | 원인 | 완화책 |
|---|---|---|
| 피격 판정 불신 | 지연/스냅샷 불안정 | MVP는 PvE 중심, 라그 보상은 제한적으로만 적용 |
| 서버 CPU 증가 | AI와 상태이상 과다 | AI 수 제한, 상태이상 종류 제한 |
| 전투 이펙트 불일치 | 클라 선연출 과다 | 서버 확정 이벤트 기반 이펙트 사용 |

## Phase 3. 인벤토리 / 루팅 / 트랜잭션

- 기간: 9~11주
- 목표: 익스트랙션 게임의 핵심인 아이템 소유권과 저장 무결성 확보

### 주요 기능

| 기능 | 상세 | 우선순위 |
|---|---|---|
| ItemInstanceId | 모든 아이템에 고유 ID 부여 | 필수 |
| Container | 상자, 시체, 월드 드랍 | 필수 |
| Inventory | 슬롯 또는 리스트 기반 소유 구조 | 필수 |
| LootRequest | 클라 루팅 요청 | 필수 |
| LootCommitted | 서버 확정 이벤트 | 필수 |
| RequestId | 중복 요청 방지용 멱등 키 | 필수 |
| Item Lock | 동시 루팅 방지 | 필수 |

### 루팅 처리 흐름

```text
Client LootRequest(itemInstanceId, containerId, requestId)
  ↓
Server Validate Distance / State / Ownership
  ↓
Server Lock Item
  ↓
Server Commit Ownership Change
  ↓
Append LootCommitted Event
  ↓
Send Ack to Client
```

### 완료 기준

- 동일 아이템을 두 명이 동시에 루팅해도 하나의 결과만 확정된다.
- 같은 requestId가 반복 전송되어도 결과가 중복 적용되지 않는다.
- 탈출 실패 시 영속 저장되지 않는다.
- 탈출 성공 시 아이템이 프로필/창고에 저장된다.

### 리스크

| 리스크 | 원인 | 완화책 |
|---|---|---|
| 아이템 복사 | 동시 루팅/재전송/크래시 | Item Lock, RequestId, Append-only Log |
| 저장 누락 | 탈출 처리와 DB 저장 분리 | RaidResult Commit 단일화 |
| 소유권 불일치 | 클라 UI 기준 이동 | 서버 소유권만 진실로 사용 |

## Phase 4. 레이드 세로 슬라이스

- 기간: 12~14주
- 목표: 한 판이 처음부터 끝까지 완주되는 최소 게임 완성

### 최소 구성

| 항목 | 수량 | 설명 |
|---|---:|---|
| 맵 | 1개 | 소형 탑다운 맵 |
| 무기 | 2개 | 연사형/단발형 |
| 적 타입 | 2개 | 근접/원거리 |
| 엘리트 | 1개 | 특성 보상 트리거 |
| 루팅 컨테이너 | 3~5개 | 상자/시체/월드 드랍 |
| 탈출 지점 | 1개 | 기본 탈출 |
| 레이드 시간 | 10~15분 | MVP 기준 세션 길이 |

### 레이드 상태 전이

```text
LOBBY
  ↓
MATCHING / SERVER_ALLOCATED
  ↓
LOADING
  ↓
IN_RAID
  ↓
EXTRACTING
  ↓
RESULT_COMMIT
  ↓
END
```

### 완료 기준

- 플레이어가 레이드에 입장한다.
- 적을 처치하고 아이템을 획득한다.
- 탈출 지점에서 일정 시간 버티면 탈출한다.
- 탈출 결과가 저장된다.
- 실패/사망 시 결과가 다르게 처리된다.

### 게이트 기준

이 단계 종료 시점에 아래 질문에 모두 “예”라고 답할 수 있어야 한다.

- 한 판을 끝까지 플레이할 수 있는가?
- 서버가 전투/루팅/탈출을 모두 확정하는가?
- 결과 저장이 일관되게 동작하는가?
- 10회 테스트에서 아이템 중복이 발생하지 않는가?

---

## Phase 5. 로그라이크 레이어

- 기간: 15~18주
- 목표: 런마다 빌드 선택이 달라지는 구조 구현

### 주요 기능

| 기능 | 상세 | 우선순위 |
|---|---|---|
| Trait Offer | 엘리트 처치/이벤트 후 3지선다 | 필수 |
| Trait Choose | 서버가 선택 확정 | 필수 |
| Trait Pool | 8개 특성 | 필수 |
| Synergy Tags | 특성별 태그 집계 | 필수 |
| Synergy Tier | 2개/4개 임계치 | 필수 |
| Curse | 강한 보상 + 디버프 | 필수 |
| Run Modifier | 런 단위 스탯 변화 | 필수 |

### MVP 특성 구성

| ID | 이름 | 효과 | 우선순위 |
|---|---|---|---|
| T01 | 출혈탄 | 히트 시 출혈 스택 | 필수 |
| T02 | 화염탄 | 화상 부여 | 선택 |
| T03 | 감전 연쇄 | 감전 스택, 제한 연쇄 | 선택 |
| T04 | 반동 교환 | 반동 증가, 피해 증가 | 필수 |
| T05 | 소음 억제 | 소음 감소, 이동/재장전 페널티 | 필수 |
| T06 | 대시 모듈 | 대시 쿨다운 감소 | 필수 |
| T07 | 전술 재장전 | 다음 탄 보너스 | 선택 |
| T08 | 응급 처치 강화 | 회복 사용 시간 감소 | 필수 |

### MVP 시너지 구성

| ID | 이름 | 조건 | 효과 |
|---|---|---|---|
| S01 | 치명적 출혈 | 출혈 태그 2/4개 | 출혈 피해 증가/취약 부여 |
| S02 | 화염 확산 | 화염 태그 2/4개 | 화상 지속 증가/사망 확산 |
| S03 | 연쇄 과부하 | 감전 태그 2/4개 | 연쇄 횟수 증가/슬로우 |
| S04 | 암살자 리듬 | 소음+이동 태그 | 은신 보너스/대시 추가 |

### MVP 저주 구성

| ID | 이름 | 페널티 | 보상 |
|---|---|---|---|
| C01 | 혈세 | 최대 체력 감소 | 피해 증가 |
| C02 | 사냥감 | 적 스폰 증가 | 희귀 루팅 테이블 접근 |
| C03 | 감지 과민 | AI 탐지 반경 증가 | 엘리트 보상 증가 |

### 완료 기준

- 레이드 중 3지선다 특성 선택이 가능하다.
- 선택 결과가 서버에 저장되고 즉시 적용된다.
- 태그 수에 따라 시너지 Tier가 갱신된다.
- 저주는 보상과 페널티가 함께 적용된다.
- 클라이언트 조작으로 특성/저주를 임의 변경할 수 없다.

---

## Phase 6. 리텐션 / 고위험 탈출 / 환경 이벤트

- 기간: 19~20주
- 목표: 반복 플레이 동기와 리스크 보상 구조 확보

### 주요 기능

| 기능 | 상세 | 우선순위 |
|---|---|---|
| 메타 해금 | 성능 증가가 아닌 선택지 확장 | 필수 |
| 고위험 탈출 | 추가 보상 대신 위험 조건 부여 | 필수 |
| 환경 이벤트 | 정전/독가스 중 1~2종 | 선택 |
| 결과 화면 | 획득/손실/특성/킬 로그 표시 | 필수 |

### 고위험 탈출 예시

```text
검문소 탈출
- 조건: 탈출 지점 노출 + AI 증원
- 성공 보상: 특성 선택 1회 추가 또는 전용 상자
- 실패 비용: 획득 아이템 손실
```

### 메타 해금 원칙

허용:

```text
특성 선택지 풀 확장
시작 장비 선택폭 확장
외형/칭호/통계 해금
```

제한:

```text
영구 피해량 증가
영구 체력 증가
과도한 시작 아이템 지급
```

### 완료 기준

- 플레이어가 위험한 탈출을 선택할 이유가 있다.
- 반복 플레이로 선택지가 늘어난다.
- 메타 성장 때문에 신규/기존 유저 격차가 과도하게 커지지 않는다.

## Phase 7. 운영 / 배포 / 안정화

- 기간: 21~24주
- 목표: 포트폴리오로 보여줄 수 있는 운영형 MVP 완성

### 주요 기능

| 기능 | 상세 | 우선순위 |
|---|---|---|
| Docker Build | Linux Dedicated Server 이미지화 | 필수 |
| Multi Instance | 레이드 서버 복수 실행 | 필수 |
| Event Log | RaidStarted, LootCommitted, DamageApplied 등 | 필수 |
| Metrics | TPS, RTT, Snapshot Size, Raid Result | 필수 |
| QA Scenario | 루팅 중복, 탈출 실패, 서버 종료 테스트 | 필수 |
| Demo Package | 플레이 영상, 아키텍처 문서, 빌드 | 필수 |

### 운영 플로우

```text
Client Request Raid
  ↓
Lobby / Matchmaker
  ↓
Orchestrator Spawn Raid Server
  ↓
Client Connect to Raid Server
  ↓
Raid Play
  ↓
Raid Result Commit
  ↓
Raid Server Shutdown
```

### 완료 기준

- Docker로 서버를 실행할 수 있다.
- 레이드 서버 인스턴스를 2개 이상 실행할 수 있다.
- 레이드 이벤트 로그가 저장된다.
- 20회 이상 테스트에서 아이템 중복이 발생하지 않는다.
- QA 실패 케이스가 문서화되어 있다.

## 11. 주간 PM 운영 방식

1인 개발 기준으로는 2주 스프린트보다 **1주 스프린트**가 적합하다.  
이유는 서버/네트워크/저장 리스크를 빠르게 노출해야 하기 때문이다.

### 주간 루틴

| 요일 | 작업 |
|---|---|
| 월요일 | 이번 주 목표 1개 확정, 백로그 정리 |
| 화요일 | 핵심 기능 구현 |
| 수요일 | 핵심 기능 구현 계속 |
| 목요일 | 통합, 예외 처리, 로그 추가 |
| 금요일 | 플레이 테스트, 버그 기록, 다음 주 우선순위 조정 |

### 매주 확인 질문

- 서버 권위가 깨진 기능이 있는가?
- 클라이언트가 결과를 직접 확정하는 코드가 있는가?
- 루팅/저장 요청은 멱등 처리되는가?
- 새 기능이 스냅샷 크기나 서버 부하를 급증시키는가?
- 이번 주 기능이 MVP 필수 항목인가?

## 15. 최종 PM 판단

이 프로젝트의 첫 개발 대상은 UI, 콘텐츠, 특성이 아니다.

**첫 개발 대상은 “전투와 루팅을 서버가 확정하는 구조”다.**

따라서 개발 순서는 아래처럼 고정한다.

```text
1. 서버 권위 뼈대
2. 전투 판정
3. 인벤토리/저장 무결성
4. 한 판 완주 가능한 레이드 플로우
5. 특성/시너지/저주
6. 운영/배포/최적화
```

이 순서를 따르면 6개월 내 MVP 완성 가능성이 있다.  
반대로 특성, UI, 콘텐츠를 먼저 만들면 3개월 차에 서버 구조를 다시 짜야 할 가능성이 높다.
